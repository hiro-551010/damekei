# Bounded Context 間連携ポリシー

## 原則

- Bounded Context 同士は**直接依存しない**（CLAUDE.md セクション4）。
- Context 間の連携が必要な場合、以下の2パターンのいずれかを使用する。
- 1つのプロジェクト内で両パターンを併用してよい。**ユースケースごとに適切なパターンを選択する**。

---

## パターン1：イベント駆動（Push 型）

あるコンテキストで起きた出来事（ドメインイベント）を、別のコンテキストが購読して反応するパターン。

### いつ使うか

- 「A が起きたら B も起きてほしい」が、A と B が異なる Context に属する場合
- 発行側が購読側の成否を気にしなくてよい場合（通知、ログ、監査 等）
- 将来的に購読者が増える可能性がある場合

### 層の責務

| 層 | 責務 |
|---|---|
| domain | ドメインイベントを定義する（`domain/events/`） |
| application | ユースケース内でイベントを発行する / 購読側はイベントを受け取りユースケースを実行する |
| infrastructure | イベントバス / メッセージブローカーの実装 |

### 設計上の注意

- 購読側は**冪等**に設計する（同じイベントが複数回届いても結果が変わらない）
- 非同期の場合は**結果整合性（Eventual Consistency）**になることを受け入れる
- イベントのスキーマは Context 間の「契約」。変更時は全購読者への影響を確認する

---

## パターン2：ACL 経由（Pull 型）

他コンテキストのデータが同期的に必要な場合、ACL（Anti-Corruption Layer）を介して取得するパターン。

### いつ使うか

- ユースケースの実行中に、他コンテキストのデータが**今すぐ必要**な場合
- 同期的なレスポンスが求められる場合（画面表示、権限チェック 等）

### 層の責務

| 層 | 責務 |
|---|---|
| domain | 自コンテキストの言葉で Port（インターフェース）を定義する |
| infrastructure | ACL を実装する。相手コンテキストの API を呼び出し、自コンテキストの型に変換する |
| application | Port 経由で ACL を呼び出す（ACL の存在を意識しない） |

### 設計上の注意

- ACL は**呼び出す側の infrastructure 層**に配置する
- 相手のデータ構造を**自コンテキストの言葉・型に変換する**ことが本質（単なる API クライアントではない）
- 呼び出し頻度が過剰な場合は Context の境界設計を見直すシグナル
- N+1 問題に注意（一括取得のインターフェースを用意する）

---

## 使い分けの判断基準

| 判断軸 | イベント駆動 | ACL |
|---|---|---|
| 通信方向 | 発行側 → 購読側（Push） | 呼び出す側 → 相手（Pull） |
| 同期/非同期 | 非同期が基本 | 同期が基本 |
| 典型的なユースケース | 「タスク完了 → 通知送信」 | 「タスク表示時に担当者名を取得」 |
| 発行/呼び出し側の関心 | 結果を気にしない | レスポンスが必要 |
| 結合度 | 非常に低い | イベント駆動より高い |

**同じ2つの Context 間でも、ユースケースによって異なるパターンを使い分ける。**

---

## 禁止事項

- Context 間の**直接的なモジュール参照**（import / require で他 Context のコードを読む）
- domain 層に**他コンテキストの概念を持ち込む**こと（ACL で変換して自コンテキストの言葉にする）
- 連携パターンの選定を**ドキュメント化せずに実装する**こと

---

## ドキュメント化

Context 間の連携を導入する際は、以下を記録する：

- 連携元・連携先の Context
- 使用パターン（イベント駆動 / ACL）
- 連携の目的
- イベントスキーマまたは ACL のインターフェース定義

記録先：該当する Context の `docs/10_contexts/<ctx>/context.md`（依存関係セクション）
