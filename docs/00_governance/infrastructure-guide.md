# インフラ判断ガイド

## 目的

インフラの技術選定において、プロジェクト横断で適用する判断基準と原則を定める。具体的なサービス名・構成は `docs/01_project/infrastructure.md` に記述する。

---

## 選定の判断軸

インフラを選定する際は、以下の優先順位で判断する。

### 1. 移行可能性（最重要）

- 特定のサービスにロックインされない構成を優先する
- アプリケーションコード（domain / application 層）がインフラの選択に依存してはならない（DDD の依存関係ルールと同じ）
- infrastructure 層のアダプターを差し替えるだけで別のサービスに移行できる設計にする

### 2. 段階的スケール

- 初期は無料枠・低コストのサービスで始める
- トラフィック・データ量の増加に応じて段階的にスケールアップする
- 「最初から本番級の構成を組む」ことを避ける

### 3. 運用コスト

- 金銭コストだけでなく、運用の手間（監視・メンテナンス・アップデート）も考慮する
- マネージドサービスを優先する（自前運用は最終手段）

---

## カテゴリ別の決定事項

プロジェクト開始時に、以下の各カテゴリについて `docs/01_project/infrastructure.md` に決定を記録する。

| カテゴリ | 決めること |
|---|---|
| ホスティング（API） | バックエンドの実行環境 |
| ホスティング（Web） | フロントエンドの配信方法 |
| DB | データベースの種類・ホスティング先 |
| 認証 | 認証基盤（自前実装 or SaaS） |
| ストレージ | ファイル・メディアの保存先（必要な場合） |
| CI/CD | ビルド・テスト・デプロイのパイプライン |
| 監視・ログ | エラー検知・ログ集約・アラート |
| DNS / CDN | ドメイン管理・キャッシュ（必要な場合） |

すべてのカテゴリが必須ではない。プロジェクトの要件に応じて取捨選択する。

---

## 移行戦略の原則

サービスを移行する際は以下の原則に従う。

### infrastructure 層での吸収

- 移行の影響は infrastructure 層に閉じ込める
- application 層・domain 層のコードを変更しない
- Repository IF やポート（インターフェース）の実装を差し替える

### 段階的移行

1. 新しいサービスの infrastructure 実装を追加する
2. テスト環境で新実装を検証する
3. 切り替える（環境変数や DI の設定変更）
4. 旧実装を削除する

### ADR の記録

インフラの移行は横断的な意思決定であるため、`docs/20_decisions/` に ADR を記録する（CLAUDE.md 5.3 参照）。

## DDD レイヤーとの対応

| DDD レイヤー | インフラとの関係 |
|---|---|
| domain | インフラに一切依存しない |
| application | インフラに依存しない。Repository IF 等のポートを通じて間接的に利用する |
| infrastructure | DB・外部 API・ストレージ等の具体的な実装を担う。**移行時に変更するのはここだけ** |
| presentation | ホスティング環境に依存する部分がある（ミドルウェア設定等） |

---

## 環境分離

最低限、以下の環境を分離する。

| 環境 | 用途 |
|---|---|
| local | 開発者のローカルマシン（Docker Compose 等） |
| test | CI / テスト用（ローカルまたは CI 上のコンテナ） |
| production | 本番環境 |

staging 環境は必要に応じて追加する（個人開発では省略可）。

環境ごとの設定は環境変数で管理する（CLAUDE.md セクション6 参照）。
